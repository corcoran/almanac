## Gap 26: Alcohol-as-meal double-counts between `log_meal` and `log_alcohol` ✅

When a drink is both calorie-bearing (it belongs in macro totals) and a
recovery-affecting alcohol event (it belongs in the alcohol overlay),
there is no documented convention for which tool to use — and no
de-duplication when both are used.

**Observed this session:**

- 5oz gin (325 kcal) was logged via `log_meal` (so it appears in
  `today.kcal_in` and the 1900-kcal cut target) AND via `log_alcohol`
  (so the recovery overlay knows about it).
- 1/2 beer on 5/10 (75 kcal) was logged the same way.

Both writes succeed silently. There is no warning in `log_alcohol` that
the caller may have already booked the kcal as a meal, no field in
`log_meal` to flag "this kcal is alcohol — don't double-book," and no
read-side reconciliation that surfaces the overlap.

**Why this matters:** the user's 5/13 daily kcal total includes the gin
*via the meal record*. If a future analysis or report also adds
`alcohol_kcal` from the alcohol session (e.g., when Gap 19 lands and
`week_to_date.alcohol_kcal` joins the snapshot), the gin will be
counted twice — 650 kcal instead of 325 — silently distorting the
deficit math.

**Suggested fix (one of):**

1. **One canonical source.** Alcohol is always logged via `log_alcohol`;
   `est_kcal` from that table is what flows into macro totals. `log_meal`
   for a drink becomes a misuse, ideally rejected or warned.
2. **Cross-reference on write.** `log_alcohol` accepts an optional
   `meal_id` to link the alcohol session to its kcal carrier;
   read-side aggregators dedupe via that link.
3. **Tag at the meal level.** `log_meal` gains an `is_alcohol: boolean`
   flag (or a `category: 'food' | 'alcohol'`) so downstream rollups can
   subtract the overlap.

Option 1 is the cleanest schema; option 2 preserves "kcal in is kcal in"
semantics; option 3 is the cheapest behavioral fix and the most flexible
for the LLM caller.

## Gap 27: MCP cannot bootstrap the first user (CLI dependency) ✅

After deleting the SQLite file and restarting the API, the first MCP
call returned:

```
API GET /v1/signals/today 401: {"error":{"code":"unauthorized","message":"No users in the database — run `seed-user` or call `update_user_profile` first."}}
```

Following the second branch of the suggestion (`update_user_profile`)
returned the same 401:

```
API PATCH /v1/users/me 401: {"error":{"code":"unauthorized","message":"No users in the database — run `seed-user` or call `update_user_profile` first."}}
```

The only working path was running the `seed-user` Node CLI manually:

```fish
ALMANAC_DB_PATH=/abs/path \
pnpm --filter @almanac/core seed-user \
  --name Jeff --dob 1981-07-16 --height-cm 183 --sex male
```

**Why this matters:**

- For local dev, it's friction (~2 minutes to dig up the CLI invocation
  and re-discover that `ALMANAC_DB_PATH` must be absolute).
- For any **deployment without shell access** (hosted MCP, remote
  agent, sandboxed CI), this is a hard block: the MCP can never create
  the first user, so the system is permanently uninitialized.
- The error message advertises `update_user_profile` as an alternative,
  but `update_user_profile` performs a PATCH that requires the user to
  already exist. The advertised path is dead.

**Suggested fix:** add a `bootstrap_user` (or `create_user`) MCP tool
that performs the equivalent of `seedUserAndPhase` — accepting at
minimum `name`, optionally `dob` / `height_cm` / `sex` / `timezone` /
`preferred_unit_system`. Return 409 if a user already exists.
Alternatively: make `update_user_profile` create-on-missing when the DB
has zero users.

Either approach removes the CLI dependency and matches the
"MCP-is-the-complete-surface" framing of the spec.

## Gap 28: `get_today_context.phase` has no "days into phase" ✅

The snapshot includes `phase.started_on: 2026-05-01` and `now:
2026-05-14T...`. Computing "day 13 of the cut" is trivial subtraction,
but it isn't surfaced.

This is half of Gap 25 (`planned_end_on`) and can land *independently*
of fixing the planned-end-date schema gap. Even without a planned end,
"days into phase" is a useful primitive that the LLM has to manually
compute on every summary.

**Observed friction:** every "where am I in the cut" summary required
me to do the date arithmetic by hand, then state "day 13 of ~61" with
the 61 coming from the notes field rather than structured data.

**Suggested fix:** add `phase.days_in: 13` to `get_today_context.phase`.
Pair with `phase.days_remaining` when Gap 25's `planned_end_on` lands;
until then, the `days_in` value alone is helpful and free.

## Gap 29: Auto-seeded phase persists past wipe → phase IDs start at 2 ✅

After deleting the DB file and re-running `seed-user`, the first
`start_nutrition_phase` MCP call returned `phase.id: 2`, not 1. The
`seed-user` CLI's `seedUserAndPhase` clearly creates a default phase
(id 1) which `start_nutrition_phase` then closes and supersedes.

**Why this matters:** mostly cosmetic, but it indicates the bootstrap
path silently seeds a phase the caller didn't ask for. If a caller
inspects the DB and finds two phase rows when they only "started one,"
that's surprising. It also conflicts with the docstring on
`start_nutrition_phase` which says it "automatically closes any
currently-active phase" — fine, but the docstring doesn't say *one
will already be active on a freshly-seeded user*.

**Suggested fix (one of):**

1. **Don't auto-seed a phase in `seedUserAndPhase`** — rename to
   `seedUser`, leave phase creation to the explicit
   `start_nutrition_phase` call. Cleanest, breaks no public contract.
2. **Document the auto-seed.** The `seed-user` CLI and any future
   `bootstrap_user` MCP tool (Gap 27) should clearly state "a default
   maintenance phase is created automatically; replace it with
   `start_nutrition_phase` to begin a cut/bulk."

## Gap 30: Sleep log summary doesn't echo the wake-date interpretation ✅

This is a **partial restatement of Gap 18** with a specific suggestion
that didn't make the priority-1-12 cut. Filing separately because the
fix is small and standalone.

`log_sleep` accepts `slept_on` (= wake date). On success it returns:

```json
{"id":1,"summary":"Logged sleep — 8h, quality 4/5.","hours":8}
```

The summary doesn't restate the date interpretation. An LLM (or user)
that read "Friday's sleep" and logged it under the wrong `slept_on`
would never see the bug in the response. This bit me earlier in this
very session: I logged "Tuesday sleep" as `slept_on: 2026-05-13`
without confirming whether the user meant Tue→Wed or Mon→Tue night.
The user caught it; the summary did not help.

**Suggested fix:** change the summary to echo the interpretation:

```
"Logged sleep — night of Tue 2026-05-12 → woke Wed 2026-05-13 — 6h, 4/5."
```

Off-by-one becomes visible at log time. This is suggested-fix-#2 from
Gap 18 and is the cheapest of the three options that gap lists. No
schema change.

## Priority suggestion (just my read, not a commitment)

If picking up Gaps 26–30:

1. **Gap 27** (bootstrap user via MCP) — blocks shell-less deployments;
   small surface; the framing of "MCP as complete interface" depends on it.
2. **Gap 26** (alcohol-as-meal double-count) — silently corrupts the
   most-watched number (daily kcal); fix before Gap 19 lands or the
   bug compounds.
3. **Gap 28** (`phase.days_in`) — free win; one subtraction; pairs
   with Gap 25 when that lands.
4. **Gap 30** (echo wake-date in sleep summary) — cheapest possible
   fix for Gap 18's off-by-one trap; one string change.
5. **Gap 29** (auto-seeded phase) — cosmetic; lowest priority, but
   ships naturally with Gap 27 if `bootstrap_user` is added.
